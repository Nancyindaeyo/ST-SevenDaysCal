# 构画路线图

基线：**3.8.0**  
复核日期：**2026-09-16**

本文只记录尚未完成的方向，不重复罗列已经落地的增量。优先级综合考虑用户影响、串聊天/写坏数据风险、实现成本和现有测试基础；它不是版本承诺。

现行行为见《[运行逻辑与规则](./运行逻辑与规则.md)》，【改】与诊断现状见《[自动改账与诊断检查](./自动改账与诊断检查.md)》，工程拆分细节见《[index.js 拆分](./engineering/index拆分.md)》。

## 一、当前功能待优化方向

### P0：切聊天期间隔离潜伏注入

#### 现状

- 切聊天会先增加边界代数并中止旧聊天的后台任务，再等待当前聊天外置数据加载，最后刷新线、面、时间戳和刻度注入。
- 在等待期间，已经发出的旧请求不会被追回；更重要的是，酒馆内存里的旧线/面/刻度 extension prompt 还没有先清空。若用户切换后立刻发送主楼，存在把上一串聊天潜伏资料带入该次生成的窗口。
- 写回侧已经有 chatId、revision、owner guard 和 abort 防护；这里关注的是“发给主楼模型的上下文”，不是旧结果写进新聊天。

#### 目标

- 聊天边界开始时立即撤掉所有聊天相关潜伏注入。
- 新聊天数据加载并确认仍是当前聊天后，再按新聊天状态恢复注入。
- 时间戳这种不含聊天剧情的固定合同可单独评估是否需要保持，但实现上必须明确分类，不能依赖时序碰巧安全。

#### 验收

1. A 聊天开启线/面/刻度注入，切到 B 后在加载窗口立即发送，生成上下文不包含 A 的账。
2. B 加载完成后，注入只包含 B 的账。
3. 连续快速切换 A → B → C 时，B 的延迟刷新不能覆盖 C。

#### 依据

- `runtime/chat-changed.js`
- `business/lines/injection.js`
- `business/outline/injection.js`
- `business/ledger/inject.js`

### P1：刻度和历法边界

#### 方向

- 为有年/无年的跨周期到期、滚周期和恢复行为补齐契约测试；不把当前止损描述成数据库事务。
- 删除中间楼后，检查刻度来源楼层及溯源引用是否仍指向有效内容。
- 历法描述与节日两步写入继续使用可确认写入，并明确第二步失败后的恢复结果。

#### 依据

- `business/ledger/`
- `business/axis/`
- 《[运行逻辑与规则](./运行逻辑与规则.md)》§10

### P1：外置存储失败要明确

#### 方向

- 在纯 TT、无文件 API 或后端能力不完整时，设置页应明确显示“不支持/未就绪”，不能让用户误以为迁移已经成功。
- 切聊天加载、迁移、CAS 冲突、结果未知分别给出可行动的状态；未知结果不能静默重试覆盖。

#### 依据

- `runtime/external-chat-storage.js`
- `runtime/storage-panel.js`

### P2：旧数据与体验抛光

- 旧聊天没有本地 `Id:` 时仍依赖标题匹配：优先做一次可回退迁移，不把 ID 塞进模型提示词。
- 面/冷知识按整份快照撤回与点/线按条撤回不一致：只有能定义稳定条目身份时再细化。
- 间引导和棱参考文本仍有局部短截断：先量化 token 与输出质量，再调整上限。
- 坐标关闭楼内收藏入口后缺少同等明显的替代入口。
- toast 是否迁入 shadow root 以真实主题冲突或遮挡反馈为触发条件。

## 二、代码待精简或拆分

原则：一次只拆一个有独立语义的块；不改变行为，不把 `index.js` 对半切，不新增只有一个实现的万能抽象。

### P0：插件生命周期

把 `index.js` 中 `_abortAllBackground`、`applyPluginEnabled` 和注入清理抽到 `runtime/plugin-lifecycle.js`。

拆分时必须显式注入 memory、timeTravel、lines、outline、space、ledger、axis generation、floor queue、theater 等 owner/controller。遗漏任何一路 abort 都应由测试失败暴露，不能静默降级。

重点回归：切聊天、关插件、热重载、在途请求、重新启用后的注入恢复。

### P1：宿主接线中块

按依赖风险分开提交：

1. `runtime/debug-payload.js`：迁出最近请求 payload 的复制和展示，风险最低。
2. `business/refresh/pace-host.js`：迁出 `readPaceSnapshot`、`paintPace`、interval 读取，DOM 作为端口注入。
3. `runtime/world-info-host.js`：承接角色/聊天/全局世界书解析、排除设置和面板端口，复用现有 `world-info-context.js` 与 `world-info-panel.js`。
4. 扩写 `runtime/generation-context.js`：迁入 participant identity、chat boundary epoch 与延迟回调闸。
5. `business/axis/date-detection-host.js`：最后迁日期检测的大 options 接线，避免先制造时旅/锚点循环依赖。

### P1：线模块 Phase 2

`business/lines/feature.js` 仍同时承担较多 generation、lifecycle、swipe/CMR 协调。下一阶段只抽薄 swipe/CMR controller：

- 保持单一 owner、chat revision 和 restore 规则。
- 一旦出现 swipe 状态漂移，停止继续拆分，先补契约测试。
- Phase 2 稳定前不做大规模 CSS/响应式重写。

### P2：机械清理

- 删除 `index.js` 中实现已迁走后留下的空节标题。
- 消除纯转发包装和完全相同的薄函数，但保留有业务语义的端口名。
- 复核 `recall.js` 相关抽块是否仅剩测试使用，再决定删除；不能只凭文件名判死代码。
- 把仓内 `*.test.js` 的统一运行方式写成脚本或贡献说明，避免依赖仓外 harness。

### 每次拆分的门槛

1. 迁移前先确认目标块已有测试，缺失时补最小契约测试。
2. 每次只提交一块并运行全部仓内 `*.test.js`。
3. 检查依赖方向：业务层不反向读取装配根，存储仍由 `store.js` / runtime 端口拥有。
4. 对生命周期改动额外验证切聊天与 abort；对数据改动额外验证 owner guard 和失败传播。

## 三、待新增功能

这些是候选能力，不代表已经排入版本。只有触发条件成立后才进入实现。

### 候选 1：TT 开启虚拟化后的 ChatSurface 适配

#### 触发条件

目标用户需要开启 TT 聊天虚拟化，并能提供稳定的 `prepareContent` / `claim` 等宿主契约。

#### 范围

- 楼内框与坐标入口跟随虚拟节点挂载/回收。
- 禁止依赖异步 observer 猜测节点归属。
- backfill 只处理宿主确认的可用窗口。

#### 风险

风险高。需要在真实 TT 环境验证，不以桌面 SillyTavern 的 DOM 行为代替。

### 候选 2：多扩展 ChatSurface 协调

当构画、柏宝书或酒馆助手热重载同时存在时，用明确 owner/claim 协议避免同一楼重复登记、重复 observer 和重复投影。只有宿主契约稳定后实施。

### 候选 3：线模块 Phase 3 响应式样式

在 Phase 2 controller 稳定后，为线页面和楼内线块补语义化 class、移动端布局和可测的状态样式。它不能与 lifecycle 重构混在同一版本。

## 当前明确不做

- 不每楼自动重查点/线/面；继续使用节拍和手动入口。
- 不让本轮拍或间引导自动代发主楼。
- 不把棱合并为其它多媒体小剧场，也不自动绑定角色卡。
- 不把稳定 ID 放进模型提示词，不为此单独升级生成 schema。
- 不做小时级刻度或子日对齐；当前时辰只用于显示和上下文。
- 不为了压 token 再截断已经按规则保留的正文/记忆。
- 不把装配根拆分当新功能前置条件；重构与产品交付分别排期。

## 建议顺序

1. 先修切聊天潜伏注入窗口，并补边界测试。
2. 抽插件生命周期，随后一次一个宿主中块。
3. 刻度/历法边界和外置存储失败态按出现顺序补齐。
4. TT 虚拟化、多扩展协调和线 Phase 3 只在对应触发条件成立后启动。
